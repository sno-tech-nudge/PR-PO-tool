# Database, as replayable SQL

Generated by `npm run handover` (or `npm run migration:export`) from the **live** database, so it is the authoritative schema. Do not edit by hand. The 40 `supabase_migration_*.sql` files in the repository root are history only and do **not** add up to this schema.

| File | What it is | Run |
|---|---|---|
| `schema.sql` | Extensions, 27 tables, columns, defaults, identity columns, keys, indexes, 11 functions, triggers, row-level-security flags and policies (public and `storage.objects`), grants, the 5 storage bucket rows | 1st |
| *(data)* | Every row, as `INSERT` statements. **Not in the repository** (private). It is `02_data.sql` in the DATA_PRIVATE package | 2nd |
| `sequences_setval.sql` | Sets every counter (identity columns, document-number sequences) back to where it was so new numbers continue the old ones | 3rd |
| `event_triggers.sql` | The two triggers that write every schema change to the append-only System Log. Must run **last**, otherwise the load itself is logged | 4th |
| `summary.json` | Row counts per table, extensions, functions, triggers, policies, buckets: use it to check a load |  |

The explained version (what each table and column means, the text values actually in use, how numbering and auto-categories work) is [`../DATA_MODEL.md`](../DATA_MODEL.md).

## Loading it

Fastest, with the private package unzipped into `db_export_backup/migration_pack/`:

```bash
TARGET_DB_URL="postgresql://postgres.<ref>:<password>@<pooler-host>:5432/postgres" node scripts/migration/apply-db.cjs
```

Or by hand, as the `postgres` role on an **empty** project: `schema.sql`, then the data file, then `sequences_setval.sql`, then `event_triggers.sql`. Full steps: [`../MIGRATION_RUNBOOK.md`](../MIGRATION_RUNBOOK.md).

To prove a package loads without touching any real database: `node scripts/migration/verify-pack.mjs` (needs `npm install`; it replays everything into an in-memory Postgres and compares every table's row count).

## Things to know

- **Supabase specifics.** The file refers to the roles `anon`, `authenticated`, `service_role`, to `storage.buckets` and `storage.objects`, and to the `pgcrypto`, `uuid-ossp`, `pg_stat_statements` and `supabase_vault` extensions. A plain Postgres needs those roles created and the storage lines removed (see the runbook, Route B).
- **The append-only lock** on `system_logs` is two triggers (`system_logs_no_change` for update and delete, `system_logs_no_truncate` for truncate) plus the function `system_logs_refuse`; a third trigger (`team_members_system_log`) writes every team change to the log; the two event triggers record every `CREATE`, `ALTER` and `DROP`. All of it is in these files.
- **Policies are wide open** (`USING (true)` on the tables, an insert-anyone policy on `system_logs`, and an all-access policy on the app's storage buckets). That is how the original works and is flagged in `START_HERE.md` as something not to copy.
- **No data is in this folder.** Rows contain bank details, PAN and Aadhaar numbers and employee records, so they are only in the private package.
